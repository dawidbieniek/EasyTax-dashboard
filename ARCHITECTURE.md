# EasyTax — architecture

Status: **skeleton only** (no features yet). This document describes the structure the features will be built into.
Deliberately lightweight: no DDD, no vertical-slice framework, no unit tests. Code is grouped by feature folder as needed.

## Stack
- .NET 10, C# 14, **Windows only** (`net10.0-windows10.0.19041.0`)
- WinUI 3 (Windows App SDK 2.6), unpackaged, self-contained
- MVVM with CommunityToolkit.Mvvm (source generators, partial properties)
- Generic Host (`Microsoft.Extensions.Hosting`) for DI, configuration and logging
- EF Core 10 + SQLite encrypted with SQLCipher (`SQLitePCLRaw.bundle_e_sqlcipher`)
- UI language: Polish, all strings in `.resw` resources

## Solution layout

```
EasyTax.slnx
Directory.Build.props      shared settings (TFM, nullable, warnings as errors, code style enforced in build)
Directory.Packages.props   central package versions
src/
  EasyTax.Core/            entities (rich, EF-mapped), rules, repository interfaces. No UI, no EF types.
    Domain/                the domain itself, one folder per feature (namespace EasyTax.Core.Domain.*)
      Clients/             Client (+ relief end date, month rules), enums, ClientPhoto, ClientValidation, IClientRepository
      Banks/ Months/ Years/  Bank, MonthRecord (+ MonthState), AccountingYear and their repository interfaces
      Limits/              LimitCalculator (VAT / cash register / ZUS Plus) and LimitStatus
    Common/                Entity base (Guid v7 id), DateOnly helpers: shared building blocks, not domain concepts
    Database/              IDatabaseInitializer: a persistence-side contract, not a domain concept
  EasyTax.Data/            EF Core: DbContext, entity configurations, repositories, DI registration
    Clients/ Banks/ Months/ Years/   configuration + repository per feature (BankSeed lives in Banks/)
    Migrations/            generated by `dotnet ef` (treated as generated code, not restyled)
  EasyTax.App/             WinUI 3 app
    Shell/                 MainWindow, navigation (service, page registry), ViewModelBase
    Dashboard/ Clients/ Settings/   one folder per feature: page + view model (+ feature services)
    Dashboard/             gauges, charts, month inputs, checklist, notes (+ ChartPalette)
    Photos/                photo picking/cropping service and the bytes-to-image converter
    Controls/              small shared UI controls (FormField)
    Localization/          ILocalizer, enum option lists
    Resources/pl-PL/       Resources.resw
    Infrastructure/        AppHost (composition root), AppPaths, DI helpers
docs/                      wireframes (reference UI) and archived drafts
```

Folders are **feature slices**, not technical layers: there is no `Abstractions/`, `Services/`, `Views/` or
`ViewModels/` folder. A feature's interface, entity, configuration, page and view model sit next to their siblings.

### Dependency rule
```
App  ──►  Data  ──►  Core
 └─────────────────►  Core
```
`Core` knows nothing about the other projects. `Data` implements the interfaces `Core` declares.
`App` is the only project that references both and wires them together.

### Domain model
Core is the domain layer, and **the EF entities are the domain entities**: plain C# classes that will carry their own
behaviour, mapped by `IEntityTypeConfiguration<T>` classes in `Data` (found by `ApplyConfigurationsFromAssembly`).
There are no separate persistence models or mappers.

Ids are **Guid v7** (`Guid.CreateVersion7()`), assigned in the `Entity` base class when the object is created.
The database never generates them (`ValueGeneratedNever`), so an object is valid before it is saved.
SQLite stores them as text.

## How a screen is built
1. Create a feature folder in `EasyTax.App` (e.g. `Clients/`).
2. `XxxViewModel : ViewModelBase`. Override `OnNavigatedToAsync` to load data.
3. `XxxPage.xaml` + code-behind. The constructor resolves the view model and sets `DataContext`:
   ```csharp
   ViewModel = App.GetService<XxxViewModel>();
   DataContext = ViewModel;
   ```
   XAML binds with compiled bindings: `{x:Bind ViewModel.Property}`.
4. Register the pair in `AppHost`: `services.AddPage<XxxPage, XxxViewModel>(pages);`
5. Navigate with `INavigationService.NavigateTo<XxxViewModel>(parameter)`.
   The navigation service calls `OnNavigatedToAsync` / `OnNavigatedFrom` on the view model.

The service locator (`App.GetService`) is used **only** for pages, because `Frame` instantiates them.
Everything else uses constructor injection.

## Cross-cutting pieces already in place
- **Navigation** (`Shell/`): `INavigationService` over a `Frame`; `IPageRegistry` maps view model → page.
  `MainWindow` hosts a `NavigationView` (collapsed icon rail) and keeps the selected item in sync.
- **Dialogs** (`Shell/IDialogService`): confirmation, "unsaved changes" (save / discard / cancel) and a generic `ShowAsync` for
  custom dialogs, all shown over the main window. View models use it; they never create UI objects. Custom dialogs
  (like the add-client form) are created by the page's code-behind and shown through the same service.
- **Navigation guard**: a view model can override `ConfirmLeaveAsync` (default: allow). The shell asks before any rail
  navigation; the client details page uses it to protect unsaved edits.
- **Forms** (`Clients/ClientForm`): one editable copy of a client's data used by both the add dialog and the details page.
  It validates (live format errors, "required" errors after the first submit), knows whether it changed
  (`HasChanges`) and converts to/from the `Client` entity. `Controls/FormField` is the small shared control that shows a label,
  the editor while editing (plain text otherwise) and the error.
- **Photos** (`Photos/`): `IPhotoService` picks, crops (centred square), shrinks (≤ 256 px) and re-encodes a picture as JPEG;
  `PhotoImageConverter` turns the stored bytes into an image for `PersonPicture`. Photos live in their own table.
- **Dashboard** (`Dashboard/`): `DashboardViewModel` is a projection of the client context plus the limit rules in Core.
  It rebuilds nothing on its own: every change goes back through the context (`UpdateCurrentRecordAsync` for month data,
  `UpdateClientAsync(id, …)` for notes and per-client checklist items) and the resulting `Changed` event refreshes the page.
  The three gauges are `LimitGaugeViewModel`s updated in place. Charts (LiveCharts2) read from three `ObservableCollection`s
  that are updated in place; the series/axes are only rebuilt when the theme changes. **Refresh rule: update, never rebuild.**
  Every `Changed` event reaches several screens, so each view model must only touch what really differs (equal values are
  skipped by the property setters; month buttons, checklist items and gauges are fixed long-lived objects updated in place (toggle buttons use `StatusToggleButtonStyle`: instant state change, no fade; note ToggleButton hover+checked is the single state `CheckedPointerOver`)
  objects). Replacing a bound list or series makes the controls re-create everything, which shows as flicker and replayed animations.
  Edits that nobody else displays (notes) are saved with `notify: false`. Notes are RTF in `Client.Notes`; the page code-behind
  converts between the editor and that string (it is a view concern) and still reads old plain-text notes. `ChartPalette` supplies their colours
  (SkiaSharp cannot use XAML theme resources): the Windows accent and the light/dark theme.
- **Client context** (`Shell/ClientContext`): the one place that knows which client, year and month are selected.
  It loads the selectable clients, the managed years and the month records of the selected client and year, restores the
  last selection from `settings.json`, snaps the selection to the join month when needed, and raises `Changed`. The app bar
  and every page showing per-client data read from it and call it to change the selection or edit the current month
  (`UpdateCurrentRecordAsync`); nobody else talks to the month repository for the selected month.
- **App bar** (`Shell/AppBar`): a user control above the page frame. Its view model is a thin projection of the client
  context; pages choose how much of it to show by overriding `ViewModelBase.AppBarMode`.
- **Settings** (`Settings/`): `ISettingsService` (`AppSettings` record, JSON file at `%LocalAppData%\EasyTax\settings.json`).
  Changing a setting raises `Changed`. A corrupt or missing file falls back to defaults.
- **Theme** (`Settings/`): `IThemeService` applies `AppSettings.Theme` (System / Light / Dark, default Dark) to the window.
- **Localization**: `ILocalizer` for strings needed in code; `x:Uid` for XAML. Source: `Resources/pl-PL/Resources.resw`.
- **Database**: file at `%LocalAppData%\EasyTax\easytax.db`; `IDatabaseInitializer` runs at startup: applies migrations,
  adds any missing banks, and seeds the years 2026–2030 once, when the database is first created.
  Enums are stored as text, dates as `DateOnly` text, ids as Guid text; deleting a client cascades to its month records and photo.
- **DI registration**: each project exposes one `ServiceCollectionExtensions` class that uses C# 14 extension blocks
  (`extension(IServiceCollection services) { public IServiceCollection AddEasyTaxData(...) }`).
- **Logging**: `ILogger<T>` from the host (debug output for now; file sink is a later task).

## Database encryption

SQLCipher, one random key per install. `DatabaseKeyStartup` runs before the database is touched: stored key that opens the database, else first start (new key shown once in `KeySetupWindow`, stored only after the user confirmed), else recovery (`KeyRecoveryWindow`). The wrapped key (DPAPI, current Windows user) lives in `easytax.key` next to `easytax.db`. `EasyTaxDataOptions.Password` carries the key into the connection string and is read when the first context is created, which is why `DatabaseInitializer` fetches the context factory lazily. A plain (old) database is refused. Details of each case are in PLAN.md (E.1 to E.5).

Debug builds: `EASYTAX_DEV_KEY=<32-character key>` skips the key windows (with `EASYTAX_DATA_DIR` and `--seed-demo` this gives a fresh encrypted demo database without typing).

## Packaging and releases

Development runs unpackaged (`dotnet run`, F5). The installed app is a signed, self-contained MSIX: `tools/Build-Package.ps1` builds it with `-p:Packaged=true` (the project then switches `WindowsPackageType` to MSIX). Identity, certificate and release flow are in `docs/RELEASING.md`; the user-facing steps are in `docs/INSTALL.md`. Releases are made by the GitHub workflow when `<Version>` in `Directory.Build.props` is raised on `main`, and the `.appinstaller` in each release points at `releases/latest/download/EasyTaxDashboard.msix`, so every computer follows the newest release at startup.

In code, `PackageInfo.IsPackaged` tells the two modes apart. It decides the data folder (`AppPaths`: the package folder when installed, so uninstalling removes the data and nothing mixes with a development build; backups default to Documents, so they survive) and the restart after a restore: a packaged app must be restarted through Windows (`AppInstance.Restart`), because starting the exe from inside the package folder would lose the package identity.

## Backups

`IBackupService` (Core) / `BackupService` (Data) do the file work; `BackupManager` (App) runs manual, scheduled and safety backups and reports with toasts; `RestoreCoordinator` is the restore flow. A backup is `EasyTax-yyyy-MM-dd-HHmm.zip` holding an encrypted copy of the database (same key as the install) and a manifest, written under a `.tmp` name and renamed when complete. Settings keep the folder (default `Documents\EasyTax\Backups`) and the automatic-backup switch; the folder itself is the record of what exists. One app instance only (`AppInstance`), which also guarantees backup and restore never overlap. A deleted client cannot come back from a restore: the database keeps a `DeletedClients` table (written in the same transaction as the delete) and `ClientDeletionService` mirrors it into `deletions.log` in the backup folder. A restore merges the backup's table, the live table and the log, removes those clients from the restored copy and tells the user how many. Tests for all of this lived in a throwaway console harness (99 checks on real encrypted files: log parsing and damage, atomic delete and apply, batching, old-schema backups, lost-database and unreachable-log scenarios) plus runs of every dialog in the real app. A suspended client has `Client.SuspendedAt` (UTC, null = active; `IsSuspended` is derived). Dev tip: set `BackupFolder` in the test data folder's `settings.json`, otherwise tests write into your real Documents.

## Third-party notices

`THIRD-PARTY-NOTICES.txt` (repo root) is generated: build, then run `powershell tools/Update-ThirdPartyNotices.ps1`, and commit the result. It lists every shipped package with its copyright and licence and holds the licence texts; the build copies it next to the exe and Settings shows it. Re-run it after adding, removing or updating a package.

## Errors, logging and toasts

- **Log:** Serilog writes `%LocalAppData%\EasyTax\logs\easytax-<date>.log` (14 days). Technical details only go there, never on screen.
- **Toasts:** `IToastService` (Shell) shows self-closing `InfoBar`s in the bottom-right corner of the main window (success and info 4 s, warning 6 s, error 8 s, at most four). View models inject it; messages are `Toast_*` resources.
- **Unexpected errors:** `App.ReportError` logs the exception and shows a toast with `UserFacingErrors.Describe` (busy / read-only / corrupt database, disk full, generic). It is reached from `Application.UnhandledException` and from `ErrorHandlingSynchronizationContext`.
- **Startup failure** (unreadable database or settings): `StartupErrorWindow` explains it and points to the log folder instead of crashing.
- **Component error state:** the clients list shows an error bar with a retry button when loading fails (`ClientsViewModel.LoadError`).
- **Toggle buttons** flip themselves on click; a handler whose save fails puts the button back (`OnAccountedClick`, `OnChecklistClick`) before rethrowing.

WinUI note (cost an hour): an exception thrown after an `await` in an `async void` method does **not** reach `Application.UnhandledException`; WinUI crashes the process (stowed exception 0xc000027b). The wrapper context catches it, but it only works when it is installed in the `App` constructor: a context set inside an async method (`OnLaunched`) is reverted when that method's first segment ends.

## Keyboard shortcuts

Declared with `Shortcuts.Add(control, key, action, modifiers)` (Shell/Shortcuts.cs) in the code-behind of the page or control that owns them; it adds a `KeyboardAccelerator` and, for buttons, a tooltip "name (key)". Plain keys are ignored while a text control has focus or a dialog/drop-down is open; chords with Ctrl or Alt always run. Focus shortcuts use `Shortcuts.FocusLater`, otherwise the text box receives the shortcut character. Keys can be changed in the one `Add` call.

| Where | Key | Action |
|---|---|---|
| Everywhere | `1` `2` `3` | Dashboard / Clients / Settings |
| Everywhere | `Esc`, click on empty space | Leave the text box (focus goes to the page, so single-key shortcuts work again) |
| App bar | `/`, `Ctrl+F` | Focus the client picker |
| App bar | `Alt+Left`, `Alt+Right` | Previous / next client |
| App bar | `,` `.` or `Left` `Right` | Previous / next month (across years) |
| App bar | `Shift+,` `Shift+.` | Previous / next year |
| App bar | `A` | Toggle accounted |
| Dashboard | `I` `S` `C` | Focus income / sales invoices / cost invoices |
| Dashboard | `N` | Focus notes |
| Dashboard | `R` `E` `U` `F` `D` `T` | Toggle VAT-R, CEIDG-1, ZUS, invoiced, ZUS DRA, tax |
| Dashboard | `J` `V` | Toggle JPK V7, VAT UE |
| Clients | `/`, `Ctrl+F` | Focus search |

WinUI notes: `KeyboardAccelerator` does not match the bracket keys (VK 219/221), so months use `,` `.`. The built-in accelerator tooltip did not show on these buttons, hence the explicit tooltips.

## Conventions
Formatting is enforced by `.editorconfig` and `.gitattributes` (tabs, CRLF, UTF-8) — never fix it by hand or by script.

C# style (compiler-enforced where possible; warnings are errors):
- Naming: `_camelCase` private fields, `I` prefix on interfaces, PascalCase for the rest; file-scoped namespaces; Allman braces.
- **`if` with a single-line condition and a single statement: no braces, statement on its own line.**
  ```csharp
  if (x is null)
  	return;
  ```
  Never `if (x) return;` on one line (build error IDE2001). Use braces when the condition spans several lines
  or the body has several statements.
- **Guard clauses over nesting**: validate and return/throw early instead of wrapping the main path in `if`s.
- One type per file; file name = type name.
- No logic in code-behind beyond view concerns.
- User-visible strings are never hard-coded: add them to `Resources.resw` (`Key.Property` for `x:Uid`, plain `Key` for code).
- Package versions only in `Directory.Packages.props`.

## Target frameworks
Windows only. Libraries (`Core`, `Data`) target `net10.0-windows` (no Windows SDK projection); the app targets
`net10.0-windows10.0.19041.0`. The unversioned library TFM is deliberate: `dotnet ef` cannot load assemblies that carry
the Windows SDK projection.

## Migrations

**Until the first release, development databases are disposable.** Do not write data-preserving migrations or custom SQL for them: change the model, delete the migrations folder, run `dotnet ef migrations add Initial` and delete old test databases. From the first release on, add normal incremental migrations (and test restoring an older backup, which migrates it).
`dotnet-ef` is a repo-local tool (`dotnet-tools.json`, run `dotnet tool restore` once).
```bash
dotnet tool run dotnet-ef migrations add <Name> --project src/EasyTax.Data --output-dir Migrations
```
A design-time factory (`EasyTaxDbContextFactory`) lets the tool run without starting the WinUI app.

## WinUI notes (things that cost time once)
- **Combo boxes: bind `SelectedItem`, not `SelectedValue`.** `SelectedValue` stayed empty when the value was set before the box was shown.
  View models expose the selected option as a property that stays in sync with the form (`SelectedGender`, `SelectedBank`, …).
  `x:Bind` cannot nest a converter binding (`Converter={x:Bind …}` does not compile) and generic converters cannot be created in XAML.
- **Showing stored image bytes**: write to an in-memory stream through `AsStreamForWrite()` and **flush**, and do not dispose the stream
  while the image is still decoding.
- **Bitmap crop bounds are in the scaled image's coordinates** (`BitmapTransform.Bounds` after `ScaledWidth/Height`), not the original's.
- **TableView** does not raise item-click or double-tap reliably; a `Tapped` handler on the grid plus a walk up to `TableViewRow` does.
- **LiveCharts controls draw on solid black** unless `Background="Transparent"` is set on each chart. Gauge series show their own
  value label by default (`DataLabelsPaint = null` removes it). Chart colours are SkiaSharp colours, so theme-dependent ones are computed
  (see `ChartPalette`) and must be rebuilt when the theme changes.
- **`ItemsRepeater` has no `IsEnabled`**; wrap it in a `ContentControl` to disable what is inside.
- A converter that looks up brushes in `Application.Current.Resources` gets the *application* theme's brush, not the element's; when
  the colour depends on the theme, compute it (as `ChartPalette` does) and bind a plain colour.
- Exceptions thrown inside `async void` event handlers do not crash the app; they are only logged. When something silently does nothing,
  reproduce the code in a throwaway console project to see the exception.
- Interactive checks: run with `EASYTAX_DATA_DIR` pointing at a temp folder and `--seed-demo`.

## Development helpers
- `EASYTAX_DATA_DIR` environment variable: use another folder for the database and `settings.json` instead of `%LocalAppData%\EasyTax`.
- `EasyTax.exe --seed-demo` (Debug builds only): fills an empty database with sample clients and 2026 month records.
  Combine both to try things out without touching real data.
